# 要求内容：駐車場検索で結果が得られない不具合の修正

## 1. 作業の概要

地図をクリックして駐車場を検索しても、最近は 1 件もヒットしなくなった。
原因を特定し、以前と同じように周辺の駐車場が表示される状態に戻す。

## 2. 不具合の内容

### 2.1 現象

- 地図上の地点をクリックして検索すると、駐車場が 1 件も表示されない
- 以前は同じ地点（萩駅周辺など）で駐車場が表示されていた
- アプリのコードは最近変更していない

### 2.2 調査で分かったこと（2026-11-26 時点）

アプリと同じクエリを、既定の検索先 `https://overpass-api.de/api/interpreter` に直接送って確かめた。

| リクエストの条件 | 結果 |
|---|---|
| 汎用の User-Agent（curl やブラウザの文字列だけ） | **HTTP 406 Not Acceptable**（nginx の HTML） |
| `Accept: application/json` を付ける | HTTP 406 |
| GET で送る | HTTP 406 |
| アプリ名を含む独自の User-Agent | HTTP 200（JSON）。ただし、再送すると 502 になることもある |
| ブラウザの User-Agent ＋ `Origin` と `Referer` | HTTP 200 になることも、502 になることもある |
| ミラー（kumi.systems、private.coffee） | 接続できない |

- 検索先の Overpass API が、**送信元を識別できないリクエストを 406 で拒否するようになった**可能性が高い。サーバー側の方針変更と考えられる
- 混雑による 502 も頻繁に返る。アプリは 502 を `network` エラーとして扱っており、429 と 504 のような「混雑」としては扱っていない
- アプリのコード（クエリの生成、応答の変換、検索結果のフィルタ）には、0 件になる原因は見つからなかった
- `useParkingSearch` と `ParkingList` は、失敗したときにはエラー表示を出す作りになっている

#### ブラウザでの確認結果

| 検索 | Network タブの結果 |
|---|---|
| 1 回目 | 応答が返らない |
| 2 回目 | HTTP 504（Overpass の処理待ちのタイムアウト） |

#### 原因

1. **Overpass API（overpass-api.de）が混雑していて、時間内に応答を返せていない**（外部の要因）
2. **アプリのタイムアウトが、サーバーの処理時間の上限より短い**（アプリの不具合）
   - クエリでは、サーバーに最大 25 秒の処理を許している（`[timeout:25]`、`buildOverpassQuery`）
   - 一方で、アプリは 15 秒で通信を打ち切る（`TIMEOUT_MS = 15_000`、`overpassParkingProvider.ts`）
   - 混雑時にサーバーが 15〜25 秒かけて結果を返そうとしても、その前にアプリが打ち切ってしまう。1 回目に「応答が返らない」のはこのためと考えられる
3. **検索先が 1 か所だけで、代わりの検索先がない**。overpass-api.de が混雑すると、検索が完全に使えなくなる

コードの変更が無くても「最近」急に起きるようになったのは、外部の要因（1）によって、アプリの弱点（2）と（3）が表に出たため。

### 2.3 未確認の事項

- 失敗したとき、画面に「0 件」とエラーのどちらが表示されているか（コード上はエラーが表示されるはず）
- 406 になる条件の公式な情報（Overpass API のお知らせや利用規約の変更）
- 代替の検索先（ミラー）を、ブラウザから使えるかどうか（CORS への対応、応答速度、利用規約）

## 3. ユーザーストーリー

- ドライバーとして、地図上の地点をクリックしたときに周辺の駐車場が表示されてほしい。目的地近くの駐車場を探せるようにするため
- ドライバーとして、検索先が混雑や拒否で使えないときは「0 件」ではなく、その理由と再試行の方法を知りたい。駐車場が無いと誤解しないようにするため

## 4. 受け入れ条件

- [ ] 原因を実際のブラウザで確かめ、design.md に記録している
- [ ] アプリのタイムアウトが、クエリで指定するサーバーの処理時間の上限より長い（定数どうしの関係を単体テストで確かめる）
- [ ] 萩駅周辺（半径 500m）を検索すると、駐車場が 1 件以上表示される（ローカル環境と GitHub Pages の両方）
- [ ] 検索先が 406 や 502 などを返したときに「0 件」と表示されない。原因に応じたエラーの文言と再試行ボタンが表示される
- [ ] 検索先 1 か所の障害で、検索が完全に使えなくなることを避ける方法を検討し、design.md で方針を決めている（代替の検索先、リトライなど）
- [ ] 追加・変更した処理に単体テストがあり、`npm run lint`・型チェック・`npm test` が通る
- [ ] Overpass API の利用規約に沿った使い方になっている（アクセス頻度の制限など、既存の `requestThrottle` の方針を守る）

## 5. 制約事項

- ブラウザの `fetch` では `User-Agent` ヘッダーを変更できない。curl で 200 になった「独自の User-Agent」の方法は、そのままでは使えない
- 外部サービスへの過剰なリトライはしない（利用規約と相手サーバーへの負荷を考慮する）
- 検索先の URL は、引き続き環境変数 `VITE_OVERPASS_URL` で切り替えられるようにする
- 提供元を Google などに切り替える対応は、今回は対象外とする

## 6. 対象外

- 駐車場データの提供元の変更（OSM 以外への移行）
- 検索機能以外の画面や機能の変更
